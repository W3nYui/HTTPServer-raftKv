# First milestone: a single application writer with Raft-backed game state

The first integrated release runs one HTTP/WebSocket application server and a three-node Raft KV cluster. Only PVP game state uses the cluster; AI games, user accounts, sessions, and chat retain their current implementations. The application server serializes each PVP room's read-validate-write operation. Raft stores one atomic JSON state envelope whose logical records are a complete snapshot for each room, an active-room index, and the next room ID; the application uses these records to recover active rooms after a restart. Ended games retain only their final snapshot; the release has no match history, replay, or query feature. A move is broadcast only after its snapshot is committed; when the cluster has no leader or quorum, the server leaves the local room unchanged and returns `raft_unavailable`. The client refreshes the latest committed game state rather than automatically replaying the ambiguous move. This deliberately does not make the application tier highly available: the existing KV protocol only supports Get, Put, and Append, so independent application servers could otherwise validate moves against stale snapshots and overwrite each other. Keeping one writer delivers a demonstrable leader-failover path without first redesigning the Raft state-machine protocol.
